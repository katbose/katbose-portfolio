The repository is a [Bun](https://bun.sh) workspace orchestrated by [Turborepo](https://turborepo.com). Applications live under `apps/`, shared configuration under `packages/`.

## Workspace layout

```text
katbose-portfolio/
├── apps/
│   ├── web/      Next.js portfolio — katbose.dev
│   ├── docs/     Mintlify docs — this site
│   ├── cms/      reserved, framework undecided
│   └── dash/     reserved, framework undecided
├── packages/
│   └── typescript-config/   shared compiler settings
├── biome.jsonc   lint + format, whole repo
├── turbo.jsonc   task graph
└── package.json  workspaces, one version for everything
```

| Workspace | Package name | Dev port | Deployed to |
| --- | --- | --- | --- |
| `apps/web` | `@katbose/web` | `7000` | Vercel, at `katbose.dev` |
| `apps/cms` | `@katbose/cms` | `7001` | its own target, separate from `katbose.dev` |
| `apps/dash` | `@katbose/dash` | `7002` | its own target, separate from `katbose.dev` |
| `apps/docs` | `@katbose/docs` | `7003` | Mintlify, served at `docs.katbose.dev` |

`cms` and `dash` are deliberately empty. They hold a `package.json` and a `README.md` and nothing else, so the structure is settled before either decision is made. Neither declares any scripts, which means `turbo run` skips them entirely rather than failing on a missing task.

<Note>
  The docs site is built and hosted by Mintlify, not by Next.js, so the two deploy independently on separate schedules.

  This site has its own subdomain, `docs.katbose.dev`, which Mintlify serves directly. `apps/web` has no `/docs` route and nothing on `katbose.dev` proxies or rewrites to it, so the two sites share only a brand and a repository. The web app's Menu badge is an ordinary cross-origin link built from `DOCS_URL` in `apps/web/app/data/siteMeta.ts`, which points at `localhost:7003` in development.
</Note>

## How content reaches the page

Everything the portfolio displays comes from one file.

```text
apps/web/app/data/portfolio.json
  → SectionRenderer          picks a component from the section's "type"
    → one component per type
      → rendered in array order
```

The file has four top-level keys:

```json
{
  "meta":     { "siteUrl": "…", "calendarUrl": "…", "email": "…" },
  "socials":  [ { "label": "GitHub", "href": "…", "icon": "github" } ],
  "posts":    [ /* essays, each rendered at /<slug> */ ],
  "sections": [ /* ordered list */ ]
}
```

`sections` is an ordered array, and the order in the file is the order on the page. Each entry carries a `type`, a `title`, and a `data` object whose shape depends on the type. `hero` is the only type without a `title`.

`socials` is consumed twice — by the floating navbar and by the contact section — so editing it once updates both.

## Server and client boundaries

The homepage is a Server Component. It creates the section tree and navigation links, then passes those rendered slots into `PortfolioShell.client.tsx`. Static prose, education and essay previews stay on the server; content JSON and its Zod schema do not become browser dependencies. Prebuild validates the content file.

Client components own only interactive state: the shell handles agent mode and QR visibility, disclosures own their expanded state, and `LiveClock.client.tsx` owns the one-second timer. Clock ticks do not rerender the entire homepage.

## Loading, themes and media

- Browser-native animations handle reveals, counters and transitions. Initial hero content is visible in server HTML before JavaScript runs.
- QR generation loads when opened. The contribution calendar, illustration images and shaders, and skill icons load as their sections approach the viewport.
- Off-screen sections use CSS content visibility until first visited. Batched intersection observers avoid repeated synchronous layout during hydration.
- Mobile and desktop navigation share the same WebGL water shader and edge shine; reduced-motion preferences disable shaders, marquee and theme transitions.
- Navbar colors use theme CSS for identical server and initial client markup. Shared theme URLs initialize before paint and follow browser history.
- Page links use native document navigation. Each navigation reloads the document instead of prefetching route code in the browser.
- DM Sans is vendored with its license under `apps/web/public/fonts/`. The layout explicitly preloads both subsets; builds do not download fonts from Google.
- Vercel Analytics loads only when `VERCEL=1`. That environment value participates in the Turborepo build cache key.

Static images use Next's responsive optimization with server-rendered `img` markup. A small adapter isolates Next's internal image helpers because the public barrel retains unused client Image code in the pinned version. Five parity tests compare it with the public API; review the adapter when upgrading Next. Illustration textures share the optimized image URL and retain a no-JavaScript image fallback.

Production builds use Next's Webpack backend; development uses Turbopack. The bundle report sums raw JavaScript referenced by generated HTML, including preload and legacy references. It excludes deferred downloads and HTML/RSC payloads. CI enforces 580 KB for the homepage and 650 KB for the essay routes. This is a bundle guardrail, not compressed transfer size or a Core Web Vitals measurement.

## Section types

Each type maps to a component in `apps/web/app/components/sections/`, and each of those exports its own `*Data` interface. The union and the renderer both live in `registry.tsx`.

| `type` | Renders |
| --- | --- |
| `hero` | Photo, name, pronunciation, live local time, intro lines |
| `experience` | A featured current role plus an expandable "previously" list |
| `techStack` | Skills as a scrolling row that expands into categories |
| `expandableCard` | A single titled card with a read-more body |
| `project` | Description, a stats grid with count-up numbers, and a link |
| `podcast` | Podcast appearances |
| `thoughts` | Essay listing, also rendered at `/explore` |
| `blogs` | Newest posts as cards plus a view-all tile |
| `education` | Schools and courses |
| `github` | Contributions graph for a username |
| `publications` | Papers with an expandable abstract |
| `recommendations` | Quotes with attribution |
| `contact` | Call-to-action buttons plus the shared social links |

Adding a type means creating the component, adding a variant to the `Section` union, and adding a case to `SectionRenderer`. Forgetting the last step is a type error at the switch, so it fails at build time rather than silently rendering nothing.

## Rich text

Any `body` or `intro` field is an array of blocks. A block is either a paragraph or a bullet list:

```json
"body": [
  "A paragraph. Supports **bold** and [links](https://example.com).",
  { "list": ["First bullet", "Second bullet with **bold**"] },
  "A paragraph after the list."
]
```

Inline syntax is limited on purpose: `**bold**` and `[text](url)`. That is the whole grammar.

## Agent mode

The same JSON is serialised to Markdown, so the human and machine views cannot disagree.

The server creates a deterministic Markdown template. Opening agent mode fills one timestamp slot using the configured timezone. The rendered text and clipboard copy use that same snapshot; a failed clipboard write leaves manual copying available. Background clock ticks do not regenerate the Markdown.

| Route | Response |
| --- | --- |
| `/<slug>` | HTML |
| `/<slug>?format=markdown` | `text/markdown` |
| `/<slug>/markdown` | `text/markdown` |

`apps/web/proxy.ts` performs the negotiation. Its matcher excludes `_next/`, `api/`, and anything with a file extension, so static assets and internal routes are never intercepted. A path that is not a real post falls through to the ordinary HTML response instead of 404-ing.

<Warning>
  `generateMarkdown` has one behaviour that looks like a bug and is not. It has no handler for the `github` section, so that section contributes nothing to the Markdown output. It is pinned by characterization tests — change it deliberately, or not at all.
</Warning>

## Tooling split

Two tools cover the repository, and the boundary between them is intentional.

**Turborepo** owns workspace-aware tasks: `build`, `typecheck`, `test`, `test:e2e`, `validate`, `dev`. It handles dependency ordering and caching.

**Biome** is not a Turborepo task. It already scans the entire repository in one fast pass, and it covers root-level files — workflows, `turbo.jsonc`, this repo's config — that no per-workspace run would ever see. Splitting it per app would be both slower and less thorough, so the root scripts call it directly.

One nuance in the task graph is worth knowing. `test:e2e` depends on `build` in the same package, not `^build` in dependencies, because Playwright's `webServer` starts `bun run start` and serves that workspace's own `.next` output. Without the same-package dependency the suite fails with "no production build found".

## Shared TypeScript config

`packages/typescript-config` publishes two files: `base.json` (ES2022, strict) and `nextjs.json` (the Next.js preset layered on top). Workspaces extend one of them rather than restating compiler options:

```json
{ "extends": "@katbose/typescript-config/nextjs.json" }
```

TypeScript tracks latest along with everything else and is currently on 7. Every direct dependency is pinned to an exact version — no `^`, no `~` — so a version change is always a visible edit to a `package.json` rather than a silent re-resolution. Transitive dependencies still carry whatever ranges their own authors declared, so `bun.lock` remains the source of truth for the full tree.
